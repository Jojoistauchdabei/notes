V8-Isolate statt Container

LXC ist die richtige Verpackung, aber die falsche Isolationslogik. Bei „1 App = 1 Container“ zahlst du 35–45 MB pro App – egal ob Docker oder LXC. Die 10–100× Gewinnung entsteht erst, wenn ein Prozess viele Apps als V8-Isolate hostet. Das LXC steht dann eine Ebene darüber.

funktioniert: stateless JS/TS/WASM funktioniert: Agent-Harness bedingt: git / npm / native Tools geht nicht: Postgres, GPU, Binaries

Die LXC-Zeile ist der ehrliche Punkt: LXC vs. Docker ist ~5–15 MB und ~200 ms, kein Faktor 10. LXC ist flinker beim Booten und braucht keinen Daemon – das ist alles. Wer „RAM sparen mit LXC“ verspricht, rechnet falsch.

Alle Tiers hängen hinter einem Caddy/Traefik ohne publizierte Ports. Skaliert wird pro Tier: erst Isolate-Idle-TTL, dann LXC-freeze, dann VM.

Als Host-Daemon nimm workerd (Cloudflare, OSS, nodejs_compat, Wrangler) – das ist der produktionsreife Pfad. nano-rs oder edge-runtime sind die Rust-Alternativen mit eingebautem VFS. Für reine Rechen-Isolate reicht auch vm.Isolate aus Node, dann hast du aber wieder 38 MB Grundlast.

3  Scale to 0 – die eigentlichen Mechaniken

  • Idle-EvictionIsolat nach 15–30 s ohne Request → Dispose(). Bei 5 ms Start ist das für den Client unsichtbar. Das ist der ganze Trick: billiges Wegwerfen statt teures Wiederherstellen.
  • CPU-Limittimer_create(CLOCK_THREAD_CPUTIME_ID) → bei 50 ms Isolate::TerminateExecution(). Bricht auch while(true){}; die Exception ist nicht abfangbar.
  • RAM-LimitHartes Limit killt den Prozess, nicht das Isolat → GetHeapStatistics() nach jedem Turn prüfen, bei Überschreitung soft evictieren (in-flight fertig, neue Requests auf neues Isolat).
  • LXC auf 0cgroup-v2-Freezer: freeze=1 → 0 % CPU. RAM bleibt aber belegt. lohnt sich erst bei fetten Workloads, nicht bei Isolaten.
  • Agent-SnapshotsSession-Start: serialisierten Heap-Snapshot erstellen, pro Turn CoW-Klon, Session-Ende: wegwerfen. Das ist „Sliver“-Restoration – ~0,3 ms statt 5 ms.

Faustregel: Scale-to-0 gehört ins Isolat, nicht ins LXC. Der Host-Daemon selbst bleibt warm (~60–80 MB). Einen 8-GB-Server „einzuschlafen“ ist keine Isolations-, sondern eine Energiefrage.

4  Was in ein Isolat passt – und was nicht

Passt rein
  • Stateless HTTP/SSR – Next, Nuxt, Svelte, Remix via Worker-Adapter
  • Edge-Logik – Auth, Rate-Limits, Webhooks, A/B, Routing, Geo
  • Agent-Harness – Prompt-Assembly, Tool-Loop, RAG, Memory, Compaction, Streaming
  • Build-Loop – Typecheck via ts-rs (Rust→WASM), Bundler via esbuild-wasm/oxc
  • Reines Datenformat – Parsen, Transcode, Regex, CSV/JSON/Protobuf
  • KI-Orchestrierung – Modellaufrufe gehen raus, Gewichte kommen nicht rein
  • Fake-Bash – Vercels just-bash (In-Memory-FS, In-Memory-Prozesse)
Passt nicht rein
  • Postgres / Redis – alles Zustandige: eine geteilte Instanz + PgBouncer
  • Inference / GPU – Größenordnung GB, meist nicht-JS
  • Native Module – better-sqlite3, sharp, canvas, bcrypt → WASM-Port oder Sidecar
  • git, ripgrep, docker – echte Prozesse: Tool-Tier oder Fake
  • Lang laufende Server – kein Listener, kein Timer-Loop, kein Worker-Thread-Pool
  • npm install – Symlinks, Lifecycle-Scripts, Binaries: in VFS richtig mühsam
  • Shared State zwischen Requests – das ist der stille Killer, nicht die CPU

Der entscheidende Punkt ist nicht das RAM, sondern die Zustandslosigkeit. Der Isolat-Schnitt bricht dort, wo ein App-Design In-Memory-Zustand zwischen Requests hat – und das ist genau der Punkt, an dem Docker bisher „kaputt“ wirkt, obwohl es funktioniert.

5  Docker effizienter hosten – was wirklich etwas bringt

  1. Vertrauenswürdige Apps: gar kein Container. systemd-Unit mit DynamicUser, MemoryMax, ProtectSystem=strict, PrivateTmp. Spart den ganzen Image-/Daemon-Pfad.
  2. Fremdcode: gVisor (runsc) statt runc. Eigener syscall-Pfad, gleiche RAM-Klasse, ~10–20 % Perf-Kost. Unprivilegierte LXC ist ungefähr gleichwertig – mit weniger Werkzeug.
  3. Datenbanken: eine Instanz pro Host. Pro App eigener Role + Schema, PgBouncer davor. Aus 12 × 300 MB werden 1 × ~120 MB + Connection-Pool.
  4. Ein Reverse Proxy für alles, keine Ports publizieren. Spart NAT-Overhead und macht TLS/Logging zu einer Sache.
  5. Platte ist der eigentliche Kostenhebel, nicht RAM. Images über 500 MB, Layer-Duplikate und Snapshots pro App vernichten den Speicher still. zram + ZFS-Kompression.
  6. Nicht verwechseln: LXC statt Docker bringt ~5–15 MB und ~200 ms. Faktor 10+ gibt es nur mit Isolaten.

7  Reihenfolge

  1. workerd in einem unprivilegierten LXC, dazu 2–3 zustandslose Apps als Test. RSS pro App messen, bevor du weitermachst.
  2. VFS + Idle-Eviction + CPU-/RAM-Guards. Erst danach ist das Setup multi-tenant-tauglich.
  3. Agent-Stack ins Isolat (just-bash, ts-rs als WASM, esbuild-wasm), native Tools in die Tool-Tier-LXC.
  4. State-Tier aufziehen – geteiltes Postgres, PgBouncer, dann Fremdcode nach gVisor/LXC. Ein Router entscheidet pro Route, welches Tier lebt.
Ehrliche Einordnung: Self-Hosting lohnt bei Datensouveränität, fehlendem Lock-in, keinem Egress und persistenten Sessions. Bei unter ~10 Mio. Requests/Monat ist Workers ($5) + Pages günstiger als ein dedizierter Server plus deine Zeit – ein 8-GB-Server kostet 40–80 €/Monat. Die Strategie aus dem Video (Inference fällt ~10×/Jahr, RAM-Preise steigen ~25–30 %/Jahr) ist trotzdem richtig: Orchestrierung gehört ins Isolat, Gewichte bleiben auf der GPU.
